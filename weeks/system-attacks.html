    Week 8 · System Attacks, Malware & Persistence¶

    🧭 CEH life cycle · Phases 3–5 — Gaining → Maintaining Access → (Covering Tracks)

    ATT&CK T1190 Exploit Public-Facing App T1068 Exploit for PrivEsc T1003 OS Credential Dumping T1021 Lateral Movement T1071 App-Layer C2 T1070 Indicator Removal

    What this page covers

    • The loop — the five-move routine you run on every host: get in → escalate → persist → steal credentials → act/pivot
    • The board — how the OS decides who can do what, and the 2×2 of identities that defines the goal
    • Each move in turn — escalation, persistence, credential theft, lateral movement, the RAT
    • Stealth vs. covering tracks, and the one idea that ties it together: malware is this loop, automated

    Last week we got through the perimeter. This week we're standing on a single machine with a foothold, and we ask the only question that matters next: now what? The answer is a routine — the same five moves run on every host you reach:

    get in → escalate → persist → steal credentials → act / pivot — then repeat on the next machine.

    Stealth runs underneath that whole routine (you're trying not to be noticed the entire time) and covering your tracks is the exit. We'll teach the whole thing on one running example — ShellShock — and translate to Windows as we go.

    1. The foothold: ShellShock¶

    ShellShock (CVE-2014-6271, 2014) is a flaw in how GNU Bash parses specially crafted environment variables. The classic web vector: a CGI web server copies HTTP headers (like User-Agent) into environment variables, Bash evaluates a malicious payload hidden in one of them, and the attacker's command runs on the server.

    The single most important thing to notice is what you become:

    $ whoami
www-data

    You land as the web server's account — www-data (or apache), a low-privilege service account. Not root. Not an administrator.

    Exploit ≠ escalation

    Running code on the box is initial access, not privilege escalation. An exploit gives you exactly the privileges the exploited process already had — no more. You're now inside one low-privilege process, and climbing higher is a separate job. (ShellShock scored CVSS > 9 not because it escalated, but because it was remote, unauthenticated, trivial to trigger, and sat on a huge number of internet-facing servers.)

    2. How a machine is built — the permission model¶

    Three layers, bottom to top: hardware → operating system (the kernel) → applications. Apps can't touch hardware directly; they ask the OS through system calls. The OS does two jobs: it mediates that access, and it enforces identity-based access control. That second job is the entire security model:

    • Every subject (a running process) carries an identity.
    • Every object (a file, another process, a device) carries permissions.
    • On every access, the kernel checks the subject's identity against the object's permissions.

    Linux writes permissions as owner / group / others, each with read, write, execute. The password hashes live in /etc/shadow:

    $ ls -l /etc/shadow
-rw-r----- 1 root shadow ... /etc/shadow

    Read that: owner root can read/write, group shadow can read, others get nothing. Our foothold is www-data — neither the owner nor in the shadow group — so the read is simply denied. That is why a foothold can't just grab the password file. Two levers matter from here:

    • root (uid 0) bypasses every permission check — which is exactly what makes it the goal.
    • setuid (the s in -rwsr-xr-x) makes a program run with the file owner's identity, not the caller's. /usr/bin/passwd runs as root for everyone because it must edit root-owned files. It's the one sanctioned exception to "a process inherits its spawner's identity" — and a prime escalation lever.
    🪟 The Windows mirror

    Objects carry ACLs instead of rwx bits; the local superuser is SYSTEM; the password store is the SAM / LSASS, not /etc/shadow. Same model — identity decides access, and SYSTEM bypasses it.

    3. The board: a 2×2 of identities¶

    Two independent questions describe every account: who it's for (human vs. service) × how much power (low vs. high).

    Low privilege High privilege
    Human ordinary user — alice human admin — a sudoer / Domain Admin
    Service low-priv service — www-data, mysql superuser — root / SYSTEM

    A foothold almost always drops you in the bottom row. The destination is the top-right cell — the local superuser — and there are three paths to it:

    1. Steal an admin's credentials → step across into the top-left, then act with that power.
    2. From bottom-left (a user account) → climb.
    3. From bottom-right (a low-priv service — this is us, ShellShock → www-data) → climb.

    Moving to the next machine is a different axis entirely — that's lateral movement (§7), not a move on this grid. And root ≈ SYSTEM: the same local-superuser role. (One wrinkle: on Windows the human-admin and SYSTEM cells are separate accounts; on Linux the top collapses to the single root, uid 0.)

    4. Where you land: the four doors¶

    Every way onto a machine arrives in one of the four cells, and the rule from §1 decides which: an exploit lands you at the privilege the vulnerable process already held.

    • ① Exploit a superuser service → lands at the top directly. EternalBlue hit SMB, which runs in the kernel's SYSTEM context — so it landed straight at SYSTEM.
    • ② Steal an admin's credentials → top-left (human admin).
    • ③ Stolen user creds / a tricked user → bottom-left.
    • ④ Exploit an ordinary app → bottom-right. This is us — ShellShock → www-data.

    Same mechanism in ① and ④; the only difference is what the vulnerable service was running as.

    5. Escalate: climbing to the superuser¶

    A shell runs at the privilege of whoever spawned it. So escalation means getting something already privileged to run your code (or stealing a higher identity's credentials). Three broad routes — and attackers don't guess, they enumerate (tools like LinPEAS / WinPEAS list every opening automatically):

    ① Exploit a bug in a privileged process or the kernel

    🐧 Linux: Dirty COW (CVE-2016-5195, a kernel race). 🪟 Windows: PrintNightmare (CVE-2021-34527, print spooler → SYSTEM).

    ② Abuse a misconfiguration (no bug — often the easiest path)

    🐧 Linux: exploitable setuid binaries (GTFOBins), overly permissive sudo, a writable root cron job. 🪟 Windows: weak service permissions, UAC bypasses, token abuse (the "Potato" family, via SeImpersonatePrivilege).

    ③ Steal a credential already on the box

    An admin password sitting in a config file or script, or cached in memory. No exploit — you just use the keys. Reused local-admin passwords make this trivial.

    6. Persist: keeping the position¶

    What you have right now is fragile. A reverse shell is a single connection the victim dials outward (firewalls scrutinize inbound far more than outbound). It dies on a reboot, on a dropped link, or — worst of all — the moment someone patches the very hole you climbed in through. Persistence means leaving something behind that re-establishes access on its own, ideally at your elevated level, so you return already at the top.

    • 🐧 Linux: a cron job, a new service, an SSH key in root's authorized_keys.
    • 🪟 Windows: a startup-folder entry, a registry run key, a scheduled task, a new service.

    Persistence is a core malware component — a RAT installs itself exactly this way.

    Real case — SolarWinds (2020)

    A backdoor (SUNBURST) hidden inside a signed Orion software update stayed dormant for ~2 weeks, then beaconed to command-and-control through traffic disguised as Orion's own. Thousands of networks, undetected for months.

    7. Steal credentials, then pivot¶

    Now that you're the superuser, the stored secrets are finally readable: the SAM (local password hashes), LSASS (credentials of recent logins cached in memory), Kerberos tickets. The classic tool is Mimikatz, which reads LSASS and extracts NTLM hashes, Kerberos tickets, sometimes plaintext.

    Often you don't even need the plaintext. Pass-the-hash replays a stolen NTLM hash directly in authentication — in NTLM the hash functions as the key, so holding it is enough. (Kerberos equivalents: pass-the-ticket, overpass-the-hash.)

    Keep it straight

    Credential dumping requires admin/SYSTEM first — it reads secrets stored on a host you already control. It is not the password-guessing you do from outside before you're in, and it is not keylogging.

    Why it's the whole game: any admin who ever logged into this box left credentials in its memory. Grab them, and you can authenticate across the network — which feeds lateral movement: using those harvested credentials to move host-to-host toward the domain controller (the server that vouches for every account), all inside the network where the perimeter firewall is blind. Each hop is a new foothold → rerun the loop.

    Real cases — Target (2013), NotPetya (2017)

    Target: entry through a phished HVAC contractor's stolen vendor login, then lateral movement to the point-of-sale network and BlackPOS malware — ~40M card numbers. NotPetya: combined stolen credentials (Mimikatz-style) with the EternalBlue SMB exploit and PsExec/WMI to spread through entire corporate networks in minutes — ~$10B in damage. A worm is this move automated.

    8. The RAT: the "act" stage, productized¶

    A Remote Access Trojan bundles the act stage into one implant: remote control + persistence + command-and-control (C2). The defender's tell is beaconing — the implant must check in with its operator, producing small, clockwork-regular outbound connections to an unfamiliar host, usually disguised as ordinary HTTPS or DNS. Same "outbound is trusted" logic as the reverse shell, now automated and persistent.

    Real case — Emotet

    Started as a banking trojan, grew into a delivery platform and botnet that rented its access to other criminals, spread via macro-laden phishing. Disrupted by law enforcement in January 2021, later resurged.

    9. Staying hidden vs. covering tracks¶

    These are two different things. Stealth is not a stage — it runs the entire time your code executes, so picture it as a band underneath the whole loop (MITRE treats Defense Evasion the same way):

    • Packing / cryptors scramble the file so signature AV finds nothing — but behavioral EDR watches what the process does at runtime, so packing buys delivery, not invisibility.
    • Process hollowing launches a legitimate process (e.g., svchost.exe) suspended, guts its memory, and runs the payload under that trusted name.
    • Rootkits tamper with the OS's own reporting so files/processes don't appear. User-mode = per-process (another tool can still spot it); kernel-mode = a driver, global, below the AV.

    Covering tracks is the exit: anti-forensics on the way out — clearing logs (event/auth/shell history), timestomping, disabling logging or tampering with alerting. The clean distinction: stealth = not noticed while you operate (continuous); covering tracks = no proof after you're gone (one-time, terminal).

    Real case — Stuxnet (2010)

    A kernel-level rootkit whose components were signed with stolen but genuine code-signing certificates (Realtek, JMicron). Hidden for months; targeted the centrifuges at Iran's Natanz facility.

    10. Malware is this loop, automated¶

    Everything above was done by hand. Map it onto a piece of malware and the picture repeats exactly:

    Stage in the loop Malware component
    get in dropper / exploit
    escalate privilege-escalation modules
    persist persistence mechanism
    steal credentials credential-theft module
    act / pivot payload + C2

    And stealth / armoring (packing, hollowing, injection, rootkits) spans every stage — it's the band, not a box. Don't read the table too rigidly: a full-featured implant can carry one tool per stage, but real samples use only the subset they need — a worm needs no C2, much ransomware skips persistence. The familiar names are just common bundles:

    • virus — infects existing files · worm — self-spreads, no user needed · trojan — disguised, run by a tricked user · RAT — ongoing remote control · ransomware — the encrypt-for-extortion payload.

    One line to take away: the loop is the spine, stealth is the band, malware is the tooling — run on every host you reach.

    Defender's view¶

    A control at every step

    Because the attacker is obligated to follow this routine, the defender gets to place a control at every step — that's what "defense in depth" means.

    Patch closes the exploit door (the #1 control — it would have stopped WannaCry and ShellShock). Least privilege limits the blast radius. EDR catches exploitation, injection, and beaconing at runtime — exactly what packing can't hide. Protect credentials with Credential Guard, LSASS protection (RunAsPPL), LAPS for unique local-admin passwords, and MFA — which would have stopped Colonial Pipeline at the front door. Telemetry (Sysmon / auditd) must be set up before an incident. Round it out with app allowlisting, limiting remote-desktop exposure, hunting persistence (Autoruns), and C2 detection (outbound beaconing).

    Recap¶

    By hand: get in (ShellShock → www-data) → escalate to root/SYSTEM → persist → harvest credentials → pivot → repeat — hidden throughout, logs cleared on exit. Automated: the same loop handed to tools (dropper, privesc, persistence, cred theft + C2) under a stealth layer — a RAT bundles several, a worm loops the whole thing, ransomware is the payoff. Next week we move up a layer: Web Attacks, where the vulnerable thing is the application itself.
