    Week 3 · Scanning, Enumeration & Vulnerability Analysis¶

    🧭 Kill chain · Phase 2 — Scanning

    ATT&CK T1595 Active Scanning T1046 Service Discovery T1018 Remote System Discovery

    What this page covers

    • The main scan types and when to use each
    • Nmap for host discovery, service/OS detection, and scripting
    • Turning open ports into real intel through enumeration
    • Vulnerability analysis — from "here's a service" to "here's an exploitable flaw"
    • How scanning looks from the defender's side

    1. Why scan?¶

    Reconnaissance (Week 2) told you who the target is. Scanning tells you what's reachable — which hosts are up, which ports are open, and what's listening. It's the bridge between "here's a domain" and "here's an exploitable service," and it's the first phase where you actually send packets to the target — which is why it needs authorization.

    Passive recon (Week 2) Active scanning (this week)
    🕵️ No packets to the target 📡 You send probes to the target
    Public data, OSINT, WHOIS/DNS Live host & port discovery
    Stealthy, low legal risk Noisy — authorization required

    2. Scan types¶

    Scanning is a trade-off between speed, stealth, and reliability:

    • TCP connect scan (-sT) — completes the full three-way handshake. Reliable and works without special privileges, but every connection is logged by the target — loud.
    • SYN "half-open" scan (-sS) — sends the SYN, reads the reply, then never completes the handshake. Faster and quieter because many systems don't log the incomplete connection. The default for most engagements.
    • UDP scan (-sU) — for connectionless services (DNS, SNMP, DHCP, TFTP). Slow and ambiguous (no response can mean "open" or "filtered"), but essential — a lot of juicy services are UDP.

    Every port comes back as open, closed, or filtered (a firewall silently dropping the probe — itself a useful signal about the network's defenses).

    3. Nmap in depth¶

    Nmap is the workhorse. The moves that matter for this course — click to expand:

    Host discovery — who's alive? 

    nmap -sn 10.0.0.0/24      # ping sweep, no port scan
    Find live hosts before you spend time port-scanning dead space.

    Service & version detection 

    nmap -sV -p- 10.0.0.5     # all 65,535 ports, identify service versions
    Turns "port 22 open" into "OpenSSH 8.9p1 — here's the exact build," which is what makes vulnerability matching possible.

    OS fingerprint + default scripts 

    nmap -O -sC 10.0.0.5      # OS guess + the safe NSE script set
    The Nmap Scripting Engine (NSE) has hundreds of scripts — from grabbing SMB shares to testing for specific CVEs.

    4. Enumeration¶

    Scanning finds the door; enumeration reads the nameplate. Once a service is identified, you interrogate it for detail an attacker can act on:

    • SMB — shares, users, group memberships, domain info (enum4linux, smbclient).
    • SNMP — full device configuration, routing tables, running processes (watch for the default public community string — a classic finding).
    • SMTP — valid usernames via the VRFY and RCPT TO verbs, which feeds password attacks later.
    • LDAP / rpcbind / NFS — directory data, exported filesystems.

    The goal is to convert "a port is open" into "here's the version, the users, the shares, and the misconfigurations I can target."

    5. Vulnerability analysis¶

    The last step of this phase is turning your service inventory into a list of exploitable weaknesses:

    • Automated scanners — Nessus and OpenVAS cross-reference each detected service/version against a vulnerability database and produce a severity-ranked report (CVSS scores).
    • Manual matching — searchsploit against the local Exploit-DB, plus the NVD (nvd.nist.gov) for CVE detail and exploitability.
    • The judgment call — not every reported vuln is real or reachable. Some need specific configs, some are already patched, some are false positives. Narrowing the scanner's output to what actually works against this target is the skill that separates a pentester from a scan-and-paste report.

    This hands you the target list for Module 4's exploitation.

    Defender's view¶

    How this looks from the SOC seat

    A ping sweep and a full port scan generate hundreds of connection attempts in seconds — high-signal, but easy to bury in internet background noise. Vulnerability scanners are louder still (they actively probe each service). Useful detection looks for one source touching many ports/hosts in a short window, often with a scanner user-agent on web ports.

    index=web_logs status=404 (useragent="*nmap*" OR useragent="*nessus*" OR useragent="*gobuster*")
| stats count by clientip | where count > 50

    Best control: you can't stop scanning, so reduce the attack surface — close unused ports, put management services behind a VPN, rate-limit at the edge, and run your own vuln scans first so you patch what the attacker would find.

    Real-world context

    The 2017 Equifax breach began with an unpatched, internet-facing Apache Struts service (CVE-2017-5638) — a flaw a routine vulnerability scan would have flagged. Scanning and vuln analysis aren't just an attacker's phase; they're the exact discipline that would have prevented one of the largest breaches in history.
