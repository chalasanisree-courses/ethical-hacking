    Week 11 · Attacking the Data Layer¶

    🔐 Data · Cracking the Vault · the crown jewels, and the two locks on them

    ATT&CK T1078 Valid Accounts T1552 Unsecured Credentials T1530 Data from Cloud Storage T1048 Exfiltration T1027.003 Steganography

    Every layer so far — network, device, application — exists to protect one thing: the data. This is the vault. Here we go after it directly.

    The one idea for the week

    The data has two locks: access control (am I allowed to read it?) and encryption (do I have the key?). You rarely break either with brute force. You become authorized, and you steal the key — then you get the data out.

    Where the data lives — the three states¶

    Data is protected differently depending on its state — which means it's stolen differently too.

    The attacks¶

    Click a step to see how it works, how to defend it, where it's bitten in the real world, and how a pentester tests for it.

    🔓 Defeat access controlReach it

    Only the DBA and the app's service account should read the database. So you become one of them: escalate to DBA (privilege escalation, Week 8), abuse an over-privileged service account, or inject straight into the query path (SQLi, Week 10) — and with SQL injection you don’t even need to be inside the network; you reach the data as an outside user hitting a web form. The lock asks "are you allowed?" — you make the answer yes. This is the same muscle as every access-control bypass in the course.

    Defense

    Least privilege — scope each service account to only the columns and rows it needs, read-only where it only displays data. Keep the DBA role to a handful of people, separate duties, and log privileged access. The tighter the grant, the less a compromised web server can reach.

    Real world

    Marriott / Starwood (2018) — attackers held access to the guest-reservation database for roughly four years, reading it freely — about 500 million guest records.

    Spot it

    Enumerate the database accounts and their grants — is the app's service account over-privileged? Can a normal web user reach data the page never needs? Test everything through the least-privilege lens.

    🔑 Defeat encryptionRead it

    Data at rest is encrypted — but here's the catch: TDE is transparent to any authorized process. Compromise the app or its service account and the database hands you plaintext; you never touch the cipher. Encryption-at-rest really defends against a stolen disk or backup — grab the encrypted files without the key and all you have is worthless glass: ciphertext, not jewels. So "beating encryption" means getting the key — from the keystore/KMS, a config file, or the server's cloud keys via SSRF (Week 10) — not cracking the algorithm. The only time you truly crack is offline, on stolen backups or password hashes (Week 5).

    Defense

    Keep keys off the box that holds the data — a managed KMS/HSM, rotated and access-logged. For the crown-jewel fields, encrypt at the application layer so even the DBA sees ciphertext. TDE and full-disk encryption still matter — for stolen drives and backups.

    Real world

    Capital One (2019) — SSRF stole the server's cloud keys and unlocked the storage. The encryption was irrelevant once the keys were gone — ~100M+ applications exposed.

    Spot it

    Ask: where are the keys? If the decryption key lives on the same host as the data, or in a readable config or environment variable, encryption-at-rest adds little against a host compromise.

    🧠 Memory scrapingRead it · data in use

    Data in transit is encrypted (TLS) and data at rest is encrypted (TDE) — but data in use, being processed, sits in memory as plaintext. So you grab it there. Point-of-sale RAM-scraping malware reads card numbers out of memory in the instant they're handled, before they're re-encrypted.

    Defense

    The hardest state to protect. Minimize how long sensitive data lives in memory, use secure enclaves / confidential computing (encrypt even in use), and hunt for the malware that does the scraping.

    Real world

    Target (2013) — RAM-scraping malware on the POS terminals lifted ~40M card numbers straight from memory as cards were swiped.

    Spot it

    Look for processes reading another process's memory, and for sensitive data lingering in memory, logs, or temp files longer than it needs to.

    📤 ExfiltrationRemove it

    Having the data isn't enough — you have to get it out, past egress filtering and DLP. So you blend in: tunnel it over an allowed protocol (DNS, HTTPS), trickle it slowly, or send it over an encrypted channel so inspection sees nothing (Week 7). The sharpest version: encrypt it with your own key before it leaves — DLP can’t read what it can’t decrypt. It’s like locking the jewels in a second vault you brought and carrying that out the front door.

    Defense

    Egress filtering and DLP to watch for bulk or sensitive data leaving, anomaly detection on outbound volume and destinations (UEBA), and blocking or inspecting unusual tunnels.

    Real world

    Equifax (2017) — the appliance that inspected outbound encrypted traffic had an expired certificate, so it was blind. Attackers exfiltrated for about 2.5 months unseen; the moment the certificate was renewed, the traffic was spotted and shut down — ~147M people exposed.

    Spot it

    Baseline normal outbound traffic; a host suddenly sending large or encrypted volumes to an unfamiliar destination is the tell.

    🖼️ SteganographyRemove it · covert

    To slip data past inspection, hide its existence — embed the stolen file inside an innocent-looking image or document. Encryption hides meaning; steganography hides that there's a message at all. (Hashing — the third idea from Week 5 — is the one you'd never use here: it's one-way, so it would destroy the data and you could never recover it after exfiltrating.) Combine encryption and steganography — encrypt, then hide — and even a found carrier reveals nothing.

    Defense

    Steganalysis — statistical analysis of carriers for odd file sizes or least-significant-bit patterns; re-encode images at the boundary to destroy hidden payloads; DLP that flags anomalous media.

    Real world

    Used in real exfiltration and malware command-and-control to evade detection — a long-standing staple of covert data theft.

    Spot it

    You'll try it yourself — hide a message inside an image and extract it again in this week's steganography assignment.

    Defender's view¶

    How you protect the crown jewels

    The data sits behind defense in depth — two locks, plus lifecycle controls:

    • Encryption — TDE for databases and full-disk encryption (BitLocker) for laptops, so a stolen drive or backup is useless. Keep keys in a KMS/HSM, off the data host.
    • Access control — least-privilege service accounts scoped to just the data they need; a tightly limited DBA role; and for files, the three models — DAC (owner decides), RBAC (by role, the enterprise standard), MAC (labels, the military model).
    • Backups — your ransomware safety net. Modern ransomware hunts the backups too, so make them immutable (write-once, locked for a set period — not even an admin can alter them).
    • End of life — delete only removes the pointer; the data stays on the disk. True sanitization is wiping (overwrite), degaussing (magnets — magnetic drives only, not SSDs), or physical shredding.
